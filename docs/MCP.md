# MCP-сервер

paratrack отдаёт агенту те же сущности, что и человеку: клиентов, контакты, сделки, активности, календарь, проекты, задачи, сессии времени и сводку по времени. Протокол: Model Context Protocol, JSON-RPC 2.0 поверх HTTP. Сервер говорит на двух ревизиях: `2025-06-18` (через `initialize`) и `2026-07-28` (версия в каждом запросе).

## Подключение

```
POST https://paratrack.duckdns.org/mcp
Authorization: Bearer pt_…
Content-Type: application/json
```

Токен создаётся в «Настройки → Токены». Токен работает в том пространстве, где его создали, и даёт права того, кто его выдал. Агент не получает больше, чем человек в форме: участник не меняет чужие сделки, а клиента создаёт только руководитель.

- Без токена или с неверным токеном ответ `401`.
- Куки браузера не принимаются. Запрос со страницы другого сайта не может выполнить инструмент от имени сессии.
- Токен «только для чтения» вызывает инструменты чтения. Инструмент записи отвечает ошибкой «Этот токен только для чтения: ничего не записано» и ничего не меняет.
- Инструменты раздела, который выключен в пространстве, исчезают из списка и отказывают при вызове. Разделы: `crm`, `calendar`, `tasks`, `goals`, `tags`, `schedule`, `invoices`, `payroll`, `integrations`. Участники и утверждённые недели доступны без раздела.

## Протокол

- Один запрос JSON-RPC на один `POST`. Пакеты (массив запросов) не принимаются ни в одной ревизии, ответ с кодом `-32600`.
- Уведомление (запрос без `id`) получает `202` без тела.
- Сессий нет: каждый запрос несёт токен.
- Методы: `initialize`, `server/discover`, `ping`, `tools/list`, `tools/call`. Остальное отвечает `-32601`; для запроса `2026-07-28` ответ ещё и с кодом `404`.
- Неизвестный инструмент или запрос без имени инструмента: ошибка протокола `-32602`.

Пример:

```sh
curl -s -X POST https://paratrack.duckdns.org/mcp \
  -H "Authorization: Bearer pt_…" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"deal_create","arguments":{"title":"Сайт для Ромашки","client_id":12,"amount_cents":250000}}}'
```

### Ревизия 2026-07-28

Запрос, который объявляет версию сам в `params._meta` (`io.modelcontextprotocol/protocolVersion`), идёт по этой ревизии: без `initialize` и без сессии. Заголовки повторяют тело:

- `MCP-Protocol-Version` равен версии из `_meta`. Иначе `400` с кодом `-32020`.
- `Mcp-Method` равен методу. Для `tools/call` ещё `Mcp-Name` равен имени инструмента; значение в виде `=?base64?…?=` декодируется перед сравнением. Нет заголовка или он не совпал: `400`, код `-32020`.
- Версия не `2026-07-28`: `400`, код `-32022`, а в `data.supported` список версий, которые сервер отдаёт.
- Каждый результат несёт `resultType: "complete"`. Список инструментов несёт `ttlMs: 0` и `cacheScope: "private"`, потому что он зависит от разделов пространства и прав токена.
- `server/discover` отдаёт поддержанные версии, возможности и имя сервера (в `_meta`).

Клиент `2025-06-18` ничего из этого не шлёт, его запросы и ответы прежние. Версия `2025-06-18` в `_meta` запроса не принимается: её клиент получает через `initialize`.

## Ошибки инструментов

Ошибка инструмента не ошибка протокола: ответ приходит результатом с `"isError": true`, а текст в нём на языке владельца токена. Агент читает текст и исправляет вызов.

- Неверное поле: текст «Проверьте поле» и имя поля, например `lost_reason`. Имена полей совпадают с аргументами инструмента.
- Нет прав: «Недостаточно прав для этого действия».
- Нет записи в пространстве: «Запись не найдена».
- Раздел выключен, токен только для чтения: см. выше.
- Аргумент, которого нет в схеме, отклоняется. Опечатка в имени поля не проходит молча.

## Аудит

Каждая успешная запись через `/mcp` попадает в журнал аудита: действие `mcp.write`, цель `имя инструмента`, примечание «агентом через MCP». Так видно, что изменение сделал агент, а не человек.

## Инструменты

Имена: `сущность_действие`. Даты в аргументах `YYYY-MM-DD`, моменты времени RFC 3339, суммы в центах, длительности в секундах. Поля, которые не переданы, не меняются, если в описании не сказано иное. Удалять клиентов, сделки и счета через сервер нельзя. Календарное событие удаляет его автор или руководитель, цель удаляет руководитель, сессию времени удаляет тот, кто её записал, шаг чек-листа удаляет участник пространства.

В пространстве остаются открытая, выигранная и проигранная стадии. Виды активности: `call`, `meeting`, `note`.

### CRM: лиды

Лид это заявка до того, как она стала клиентом и сделкой. Любой участник читает лиды, создаёт их, правит и пишет в их ленту. Сменить статус и перевести лид в клиента может владелец лида или руководитель. Назначить другого ответственного может только руководитель. Лид переводится в клиента один раз: клиент берёт почту лида, контакт и сделка создаётся на первой открытой стадии. После перевода лид закрыт, и его статус не меняется.

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `lead_list` | `status`, `owner_id` | Лиды пространства, новые сверху. Статус: `new`, `contacted`, `qualified`, `lost`, `converted`. |
| `lead_create` | `company`, `contact_name`, `phone`, `email`, `source`, `message`, `owner_id`, `next_step_at` | Записывает лид. Нужно одно из: компания, контакт, телефон или почта. Статус `new`, владелец по умолчанию токен. |
| `lead_update` | `lead_id`*, `company`, `contact_name`, `phone`, `email`, `source`, `message`, `owner_id`, `next_step_at` | Меняет поля, которые переданы. Владельца меняет только руководитель. Лид должен оставаться с контактом. |
| `lead_status_set` | `lead_id`*, `status`*, `lost_reason` | Ставит статус `new`, `contacted`, `qualified` или `lost`. В `lost` нужна причина, уход из `lost` её очищает. Статус `converted` ставит только `lead_convert`. |
| `lead_convert` | `lead_id`* | Только руководитель: переводит открытый лид в клиента и сделку. Письмо лида уходит клиенту, сообщение лида становится первой заметкой сделки. Если клиент с таким названием уже есть, отказ с полем `client name`, и ничего не записывается. |
| `lead_activity_add` | `lead_id`*, `kind`, `body`, `result`, `occurred_at` | Записывает звонок, встречу или заметку в ленту лида. Ленту читает `activities_list` с `lead_id`. |
| `lead_response_stats` | `from`*, `to`* | Время первого ответа по лидам, созданным с `from` по `to` (даты `YYYY-MM-DD`, оба дня входят, по часовому поясу пространства). Возвращает число созданных, число с хотя бы одной активностью, число с ответом в пределах 120 минут и медиану минут до первой активности (`null`, пока ответов нет). Читает любой участник. |

Ключ приёма заявок с сайта инструментом не является. Руководитель создаёт его в приложении, а сайт отправляет заявки на `POST /api/leads/intake` с заголовком `X-Intake-Key`. Агент эту точку не вызывает.

### CRM: воронка

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `funnel_report` | `from`*, `to`* | Воронка за период (даты `YYYY-MM-DD`, оба дня входят, по часовому поясу пространства). ### Участники, счета, ведомости, утверждённые недели

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `members_list` | | Участники с id, именем, email и ролью. Только руководитель. |
| `invoices_list` | | Счета: номер, клиент, статус, период, срок оплаты, суммы в центах. Только руководитель. |
| `invoice_get` | `invoice_id`* | Один счет со строками и журналом оплат. Только руководитель. |
| `payroll_runs_list` | | Ведомости выплат: номер, период, статус, суммы. Только руководитель. |
| `timesheet_approvals_list` | `from`*, `to`* | Утверждённые недели, пересекающие дни от и до включительно. Видят все участники. |
| `invoice_draft_create` | `start`*, `end`*, `client`, `project_id` | Создаёт черновик счёта из часов периода, как страница счетов. Период включает оба дня. Не создаёт, пока в периоде есть неутверждённые недели или часы уже стоят в другом счёте. Без `client` берётся клиент проекта. Только руководитель. |
| `invoice_mark_sent` | `invoice_id`* | Переводит черновик в отправленный, как кнопка «Отметить отправленным» на странице счёта. Обратно в черновик не переводится. Только руководитель. Необратимо. |
| `invoice_send` | `invoice_id`*, `email` | Отправляет счёт клиенту письмом с PDF. Без `email` берётся адрес клиента из счёта. Счёт становится отправленным, когда письмо доставлено. Только руководитель. Необратимо: письмо уходит клиенту. |
| `invoice_record_payment` | `invoice_id`*, `amount_cents`*, `paid_on`*, `note` | Записывает оплату в журнал. Сумма не больше того, что ещё не оплачено. Когда оплат хватает, счёт становится оплаченным. Записанная оплата остаётся в журнале. Только руководитель. |
| `payroll_run_create` | `start`*, `end`*, `notes` | Создаёт черновик ведомости за период по утверждённому времени. Не создаёт, если в периоде есть неутверждённое время или период пересекается с существующей ведомостью. Только руководитель. |
| `payroll_run_pay` | `run_id`* | Отмечает ведомость выплаченной. Деньги этот инструмент не переводит: выплата идёт вне системы. Участникам уходит уведомление. Только руководитель. Необратимо. |
| `timesheet_week_approve` | `week_start`* | Утверждает прошедшую неделю табеля; `week_start` первый день недели пространства. Открыть утверждённую неделю можно только в табеле. Только руководитель. |

Удалять счета и ведомости, открывать утверждённую неделю и удалять пространство агент не может: он только ставит запрос в очередь (ниже), а подтверждает его человек в приложении. Возвращать оплаченную ведомость нельзя. Отправка счёта и выплата ведомости доходят до клиента и участников и не отменяются.

### Очередь подтверждений

Четыре действия агент может только запросить. Запрос ждёт в очереди, пока человек подтвердит его или отклонит в приложении: «Настройки» → «Подтверждения». Страница видна владельцу и администраторам. Удаление пространства подтверждает только владелец. Подтверждение выполняет то же действие, что соответствующая страница, от имени того, кто подтвердил, и его правилами. Если действие отказало, запрос остаётся в журнале со статусом «не выполнен» и причиной. Страница показывает решённые запросы под ожидающими: выполнено, не выполнено с причиной или отклонено. Отклонение ничего не выполняет. Токен агента не может подтвердить или отклонить запрос: эти действия доступны только в браузере.

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `invoice_delete_request` | `invoice_id`*, `reason`* | Просит удалить черновик счёта. Ничего не удаляет. Отправленный счёт не запрашивается. Только руководитель. |
| `payroll_run_delete_request` | `run_id`*, `reason`* | Просит удалить черновик ведомости. Ничего не удаляет. Выплаченная ведомость не запрашивается. Только руководитель. |
| `week_reopen_request` | `week_start`*, `reason`* | Просит снять утверждение недели, как кнопка на табеле. `week_start` первый день недели. Ведомость, покрывающая неделю, останавливает снятие при подтверждении. Только руководитель. |
| `workspace_delete_request` | `reason`* | Просит удалить пространство. Подтвердить может только владелец. Пространство с другими участниками при подтверждении не удалится. Только владелец. |

Повторный запрос на тот же объект, пока первый ждёт решения, возвращает уже стоящий в очереди запрос.

### Администрирование: только чтение

Эти инструменты читают то же, что страницы настроек. Ни один не отдаёт секрет: ни подпись вебхука, ни токен, ни ключ, ни ссылку-приглашение.

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `webhooks_list` | | Адреса вебхуков, события, активен ли, последняя доставка. Только владелец, как страница вебхуков. |
| `integrations_list` | | Интеграции: провайдер, имя, состояние (`ok` или `failed` с текстом последней ошибки синхронизации), дата подключения. Видят все участники. |
| `api_tokens_list` | | Свои API-токены: id, имя, префикс, только чтения, создан, последнее использование. Чужие токены не видны. |
| `workspace_settings_get` | | Имя, часовой пояс, первый день недели, автоблокировка, валюта, округление, префикс счёта, НДС и примечание, реквизиты. Вместо ключа Stripe только `stripe_key_set`. Только руководитель. |
| `invitations_list` | | Приглашения: состояние (`open`, `accepted`, `expired`), роль, создано, истекает. Отозванное приглашение удаляется и в списке не появляется. Только руководитель. |

`*` отмечает обязательный аргумент.

## Что не входит

- Потоковые ответы (SSE) и OAuth. Токен `pt_` единственный способ входа.
- Пакеты JSON-RPC.
