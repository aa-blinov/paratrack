# Рабочий цикл фичи

Каждая фича проходит один и тот же путь. Ни один этап не пропускается, а выход из проверки
возвращает фичу на этап, который её поломал.

```
спецификация → реализация → автотесты → проверка агентом по персонам → ворота
      ↑                                                                    │
      └──────────────── найденное становится задачами в том же change ◄────┘
```

## Этапы

| # | Этап | Что делаем | Команда или артефакт | Выход |
|---|------|------------|----------------------|-------|
| 1 | Спецификация | OpenSpec change: `proposal.md`, `design.md`, `specs/`, `tasks.md`. Цели и аудитории пишутся в proposal. | `openspec-propose` / `opsx:propose` | Утверждённый change |
| 2 | Реализация | Задачи по порядку, каждая задача закрывается отдельным коммитом. Бандл UI пересобирается вместе с кодом. | `openspec-apply-change` / `opsx:apply` | Все задачи отмечены |
| 3 | Автотесты | Набор, который задевает изменение: `scripts/test.sh` на пакетах, `vitest`, `tsc`, архитектурная проверка. Перед выходом на этап 4 весь `make verify` на дереве. | `make verify`, `scripts/test.sh ./internal/...` | Зелёный прогон, лог сохранён |
| 4 | Проверка агентом | Claude-агент через встроенный браузер проходит сценарии персон на локальном стенде с засеянными данными. | `e2e/agent/journeys/*.md`, отчёт в `e2e/reports/` | Отчёт с вердиктом по каждому сценарию |
| 5 | Ворота | Сверка отчёта с критериями ниже. Найденное становится задачами в том же change, цикл повторяется с этапа 2. | `e2e/agent/REPORT.md` | Вердикт: пройдено или возврат |

### Критерии ворот

Фича считается готовой, когда выполнено всё из списка:

- этап 3 зелёный на полном дереве, лог приложен к отчёту;
- каждый сценарий персоны, который затрагивает фича, пройден без «красных» шагов;
- нет ошибок в консоли браузера на затронутых экранах;
- персона не видит того, что стоит в её `must_not_see`;
- отчёт ссылается на коммиты, которые проверял.

Любой «красный» шаг возвращает фичу на этап 2. Ответ «это не баг, так и задумано» записывается
в `design.md` с обоснованием, иначе это остаётся дефектом.

## Разделение по аудиториям

Продукт обслуживает разные аудитории, и у каждой свой набор функций. Фича относится к той
аудитории, для которой она сделана, и проверяется персонами этой аудитории и соседними.

| Аудитория | Персона | Что ведёт | Что не должна видеть |
|-----------|---------|-----------|----------------------|
| Отдел продаж | Галина | клиенты, счета, отчёт по клиенту | выплаты участникам, настройки команды |
| Разработка | Сергей | задачи, таймер, теги, статистика | счета, выплаты, настройки команды |
| Руководитель и владелец | Александр | согласование недель, выплаты, настройки команды, закрытие правок | — |
| Фрилансер | Мария | личное время, табель, цели, счёт клиенту | команда, выплаты участникам |

Данные персон живут в `e2e/personas/personas.json`. У каждой персоны своя компания, свой
аккаунт и свои данные, поэтому никто не видит чужих клиентов, времени и денег.

## Воспроизводимость

- Стенд поднимается одной командой: `bash scripts/qa-env.sh up`. Он пересобирает сервер из дерева.
- Данные персон создаёт `python3 e2e/personas/seed.py`. Повторный запуск ничего не дублирует.
- Агент работает по сценариям из `e2e/agent/journeys/`, а не по памяти. Каждый шаг записан
  с ожидаемым результатом.
- Отчёт пишется по шаблону `e2e/agent/REPORT.md`, с датой, коммитом и версией стенда.

Пошагово для одного прогона:

```bash
bash scripts/qa-env.sh down && bash scripts/qa-env.sh up
PARATRACK_BASE=http://127.0.0.1:8890 python3 e2e/personas/seed.py
# дальше агент проходит сценарии персон по e2e/agent/journeys/ и пишет отчёт в e2e/reports/
```
