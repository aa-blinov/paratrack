# Эксплуатация paratrack

Что нужно знать тому, кто продаёт сервис, а не просто гоняет его у себя.
Черновик; процедуры с пометкой «проверено» прогнаны на живом стенде.

## Бэкапы

Ночной дамп: `scripts/backup-s3.sh` в cron, цель — S3-совместимое хранилище
(B2), ключи и бакет в `.env`. Хранение 30 дней (`KEEP_DAYS`), очистка по
метке времени в имени файла. Ошибки улетают в Sentry Cron Monitor
`paratrack-backup` (`PARATRACK_SENTRY_DSN`); без DSN проверка тихо
пропускается — то есть отсутствие алерта при пустом DSN не значит, что дампы
идут. Проверяйте руками: `aws s3 ls s3://$S3_BUCKET/daily/ | tail`.

**Проверка дампа без прод-базы**: `scripts/backup-s3.sh --verify` — разворачивает
новейший дамп в одноразовый Postgres и печатает счётчики строк против живой
базы. Запускать после каждого обновления схемы, минимум раз в месяц.

**Восстановление прод-базы** (проверено на стенде, см. ниже):

```
aws s3 cp s3://$S3_BUCKET/daily/<stamp>.sql.gz - | gunzip | \
  docker compose exec -T db psql -q -v ON_ERROR_STOP=1 -U paratrack -d paratrack
```

Три правила:

1. `ON_ERROR_STOP=1` обязателен: без него psql проглотит середину дампа и
   скажет «готово».
2. Дамп разворачивается в пустую базу. Вливать поверх живой без очистки
   нельзя: команды `CREATE TABLE` без `IF NOT EXISTS` упрутся в существующую
   схему. Полная гибель базы = очистить том или поднять новый, потом дамп.
3. После восстановления бинарник сам дотащит схему до актуальной: миграции
   идемпотентны и выполняются при старте под advisory-блокировкой.

**Репетиция восстановления** (проверено, `DRILL PASSED`): зарегистрировать
аккаунт и две сессии через приложение на выбрасываемой базе; `pg_dump` тем
способом, что в скрипте; уничтожить контейнер целиком; восстановить в
свежий Postgres; запустить сервер и войти спасённым паролём. Счётчики строк
до/после совпали, вход выдал 303 и сессионную куку. Повторять репетицию при
каждом смене процедуры бэкапа.

## Мониторинг

- **Sentry**: `PARATRACK_SENTRY_DSN` в env. Ошибки сервера и браузера идут
  через собственный `/sentry-tunnel`. Алерты: минимум на 5xx-всплеск и на
  молчание cron-монитора бэкапов.
- **Аптайм**: внешний проверяльщик на `/` (редирект на /login — это норма)
  и на `GET /static/manifest.webmanifest` (лёгкий, без БД).
- **Диск**: дампы в бакете чистятся сами; следить за местом на хосте не
  приходится, но паранойя раз в неделю в `docker system df` не помешает.

## Первая живая транзакция Stripe

До сих пор ни одной оплаты не проводилось; путь покрыт юнит-тестами,
но не живым провайдером. Порядок первого прохода:

1. Тестовый режим: ключи `PARATRACK_STRIPE_KEY` +
   `PARATRACK_STRIPE_WEBHOOK_SECRET` из тестового дашборда Stripe.
2. Выставить счёт с оплатой, пройти Checkout тестовой картой, убедиться:
   журнал платежей получил строку, счёт стал `paid`, вебхук пришёл и
   подпись прошла.
3. Повторить с отклонённой картой: счёт остаётся `sent`, ошибки нет в
   интерфейсе, ошибка в логах только категорией.
4. Повторить оплату дважды (идемпотентность): второй вебхук того же события
   не должен удвоить запись.
5. Живой режим: те же ключи из живого дашборда, одна реальная карта,
   возврат из дашборда Stripe. После этого можно принимать деньги.

## Первый живой OIDC

Проверено против Dex v2.46.1 в Docker (ноябрь 2026), полный цикл:
discovery по http в dev-режиме, PKCE S256, обмен кода, JWKS, userinfo,
создание аккаунта, повторный вход по субъекту и запрет входа в занятый
паролем аккаунт. Порядок для нового провайдера:

1. Зарегистрировать приложение у провайдера, redirect
   `https://<host>/sso/callback`.
2. `PARATRACK_OIDC_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET`.
3. Войти, проверить: аккаунт создан, `email_verified` от провайдера обязателен
   (иначе отказ на странице логина с кодом `bad_email`), выход из
   неподтверждённого аккаунта уходит на восстановление пароля.
4. Смена адреса в профиле без подтверждения — известное ограничение
   (docs/PRODUCT.md, «Known limitations»).

Локальная проверка с Dex (стиль выше: скрипт `e2e/sso_local_run.py`,
порядок сборки стенда в истории коммита «oidc: живой прогон против Dex»):

```
docker run -d --name dex -p 127.0.0.1:5556:5556 dexidp/dex:v2.46.1 \
  dex serve /etc/dex/config.yaml
# config: staticPasswords с bcrypt-хешем пароля (хеш можно взять из
# users.password_hash после регистрации в paratrack), staticClients с
# redirect http://127.0.0.1:8890/sso/callback, skipApprovalScreen: true
PARATRACK_OIDC_ISSUER=http://127.0.0.1:5556/dex \
PARATRACK_OIDC_CLIENT_ID=paratrack \
PARATRACK_OIDC_CLIENT_SECRET=... ./paratrack web --addr 127.0.0.1:8890
.venv/Scripts/python e2e/sso_local_run.py user@x.test <пароль>
# FINAL_URL с сессией — вход; /forgot-password?error=sso_unconfirmed —
# аккаунт с тем адресом уже занят паролем, и его не отдали.
```

## Известные ограничения сегодня

- `staticcheck` вне `verify` (несовместимость с Go 1.27.4, задокументировано
  в Makefile) — не влияет на прод, влияет на гигиену разработки.
- Rate limiting per-process: масштабирование в несколько инстансов за
  балансировщиком потребует выноса лимитеров. Для одного бинарника — норма.
- Бэкапы снимают Postgres; файлов задач (они в БД) это покрывает.
