# mcp-server Specification

## Purpose
Агент работает с платформой теми же сущностями, что и человек, но через протокол MCP. Сервер не вводит новую авторизацию: вход тот же токен `pt_`, что у `/api/v1`, и права пользователя, который его выдал.

## Requirements

### Requirement: Протокол и транспорт

Сервер SHALL отвечать на `POST /mcp` по JSON-RPC 2.0 и поддерживать методы `initialize`, `ping`, `tools/list` и `tools/call`. Ответ MUST быть JSON. Сервер MUST согласовать версию протокола с клиентом и отвечать версией, которую поддерживает. Уведомления без `id` MUST получать ответ 202 без тела.

#### Scenario: Рукопожатие
- **WHEN** клиент присылает `initialize` с поддерживаемой версией протокола
- **THEN** сервер отвечает той же версией, списком возможностей с инструментами и именем сервера

#### Scenario: Неизвестная версия
- **WHEN** клиент присылает версию, которую сервер не поддерживает
- **THEN** сервер отвечает поддерживаемой версией, и клиент решает, продолжать ли

### Requirement: Аутентификация

Каждый запрос `/mcp` MUST нести заголовок `Authorization: Bearer pt_…`. Запрос без токена или с недействительным токеном MUST получать HTTP 401. Сервер MUST NOT принимать cookie-сессию для `/mcp`.

#### Scenario: Запрос без токена
- **WHEN** запрос приходит без заголовка авторизации, даже с действительной cookie-сессией
- **THEN** сервер отвечает 401

#### Scenario: Токен только для чтения
- **WHEN** токен создан с флагом «только чтение» и агент вызывает инструмент записи
- **THEN** инструмент возвращает ошибку «токен только для чтения», данные не меняются

### Requirement: Инструменты над сущностями

Сервер SHALL предоставлять инструменты для клиентов, контактов, сделок, активностей, событий календаря, проектов, задач, сессий времени, сводного отчёта, целей, тегов, участников (руководителю), плана по неделям, счетов и ведомостей (руководителю, только чтение для счетов и ведомостей). Инструменты счетов (черновик, отметка отправленным, отправка письмом, запись оплаты), ведомостей (черновик, отметка выплаченной) и утверждения недели SHALL быть доступны только руководителю, с той же проверкой, что на странице. Сервер MUST NOT предоставлять инструменты, которые удаляют счета, ведомости или пространства, или открывают утверждённую неделю напрямую. Эти действия запрашиваются через очередь подтверждений (инструменты `*_request`), и каждое подтверждает или отклоняет человек в приложении. Ни один инструмент MUST NOT подтверждать, отклонять или выполнять запрос. Каждый инструмент MUST иметь описание и JSON-схему входа. Инструмент MUST проверять права так же, как соответствующий экран или `/api/v1` для того же пользователя.

#### Scenario: Список инструментов
- **WHEN** клиент вызывает `tools/list`
- **THEN** ответ содержит инструменты с именами вида `clients_list`, `deal_move_stage`, `calendar_event_create`, `time_session_start`, и у каждого есть `inputSchema`

#### Scenario: Права пользователя
- **WHEN** агент от имени участника без права управления вызывает `client_update`
- **THEN** инструмент возвращает ошибку «нет прав», как сделал бы экран

### Requirement: Ошибки инструментов

Ошибка выполнения инструмента MUST возвращаться как результат инструмента с `isError: true` и текстом, понятным агенту. Ошибка протокола (неизвестный метод, неверный JSON-RPC) MUST возвращаться как JSON-RPC error. Ни один ответ MUST NOT содержать внутреннюю трассировку или текст SQL.

#### Scenario: Неизвестный инструмент
- **WHEN** клиент вызывает инструмент, которого нет
- **THEN** сервер отвечает JSON-RPC ошибкой с кодом «метод не найден»

#### Scenario: Ошибка данных
- **WHEN** агент передаёт дату окончания раньше начала события
- **THEN** инструмент возвращает `isError: true` с текстом «конец раньше начала»

### Requirement: Аудит

Каждый успешный вызов инструмента записи MUST попадать в журнал пространства с именем инструмента, пользователем и источником «агент». Вызовы чтения журнал MUST NOT писать.

#### Scenario: Запись через агента
- **WHEN** агент создаёт сделку
- **THEN** журнал показывает «сделка создана агентом» от имени владельца токена
