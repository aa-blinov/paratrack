# Design

## Context

Проект хранится на активности (`activities.project_id`). Сессия времени ссылается на активность, и все расчёты по проекту идут через эту связку. Назначение проекта `AssignActivityProject` переписывает `activities.project_id`, а защищены только сессии с `invoice_id`. Старт таймера (`StartActivity` в `internal/trackingops/service.go`) вызывает `AssignActivity`, если в запросе передан проект. Поэтому старт с другим проектом переписывает историю всей активности.

Правка сессии идёт через `tracking.Service.UpdateSessionFields` и `db.UpdateSessionFields`. Журнал аудита (`audit_log`) пишет веб-слой через `AuditLog.Record` уже после операции, отдельным запросом, и ошибку только логирует. Значит, запись «в той же транзакции» требует, чтобы БД писала её внутри правки.

Места, которые читают проект через активность, найдены поиском по `a.project_id` и JOIN с `activities`. Из них расчёты по проекту по времени: `project_activity_queries.go` (`ProjectSpans`, `ProjectSessions`, `ProjectTrackedTotal`), `invoice_lines.go` (`BuildInvoiceLines` и неоплаченные суммы), `clients.go` (итоги клиента), `session_queries.go` (фильтр по проекту), `timesheet.go` (проект строки), `scheduling.go` (минуты проекта), `project_assignments.go` (неназначенные активности). Остальные места читают активность или её задачу (`ProjectActivityCounts`, `ProjectActivities`, `tasks.go`, `imports.go`) и не меняются. `invoice_legacy.go` — разовая миграция истории 2026-09-27: колонка новая и пустая в момент миграции, поэтому её не трогаем.

## Decisions

### D1. Переопределение проекта хранится на сессии

Добавляется nullable-колонка `sessions.project_id` (FK на `projects`). Действующий проект сессии вычисляется как `COALESCE(sessions.project_id, activities.project_id)`. Во всех местах из Context читаем именно это выражение, а не `activities.project_id`.

Альтернативы:
- Переносить сессию в другую активность с нужным проектом. Отклонено: активность идентифицируется названием (см. память проекта), дубли уже есть, и появятся активности «по проекту». Отчёты по названию сломаются.
- Запретить смену проекта при старте и в правке. Отклонено: не закрывает TIME-11, а правка ошибок нужна.

Миграция аддитивная: колонка nullable, существующие строки получают NULL и продолжают работать как раньше. Откат: убрать колонку и вернуть `activities.project_id` в запросах, в данных ничего не теряется.

### D2. Старт с проектом

- Если активность без проекта и у неё ещё нет сессий, проект назначается активности, как сейчас: история не меняется, потому что её нет.
- Во всех остальных случаях проект, отличный от проекта активности, записывается на новую сессию (`sessions.project_id`). Проект активности и прошлые сессии не меняются.
- Если выбранный проект совпадает с проектом активности, переопределение не пишется: сессия наследует проект.

Это поведенческое изменение для старта, уже отмечено в proposal как BREAKING.

### D3. Правка проекта одной сессии

`SessionUpdateRequest` получает поле проекта: значение задаёт переопределение, ноль снимает его и возвращает наследование от активности. Правка отклоняется, если сессия входит в счёт (`invoice_id`) или неделя утверждена (существующие `lockApprovedWeek` и `lockApprovedSessionStart`). Проверку выполняем в той же транзакции, что и запись.

### D4. Аудит в той же транзакции

`db.UpdateSessionFields` после блокировки сессии сравнивает старые и новые значения полей и пишет по записи в `audit_log` на каждое изменённое поле, внутри своей транзакции (тип `model.AuditRecord`, действие `session.edit`, цель `session:<id>`, в meta поле, было и стало). IP приходит в `SessionUpdateRequest` от веб-обработчика, потому что БД его не знает. Если правка не сохраняется, транзакция откатывается и записей не остаётся. Значения времени пишем в том виде, в котором их хранит БД; отображение в журнале — отдельный пункт ADM-02.

### D5. Расчёты по действующему проекту

Расчёты по времени переводятся на `sessionProject` (`COALESCE(s.project_id, a.project_id)`). Неоплаченные суммы теперь группируются по активности и собственному проекту сессии, чтобы сессия с переопределением уходила в свой проект. Пока колонка не заполнена, результаты совпадают со старыми; тест `TestEffectiveProjectCountsASessionUnderOneProject` проверяет один проект на каждое чтение.

## Risks

- Пропущенное место в расчётах даст расхождение между отчётом по проекту и счётом. Смягчение: тест «сессия с переопределением попадает ровно в один проект» по каждому отчёту из списка.
- Аудит внутри транзакции удлиняет правку на одну вставку. Для правок времени это приемлемо.
- Переопределение на выставленной сессии недопустимо. Отказ нужно показать пользователю понятным текстом (отдельный пункт TIME-03 не входит, но сообщение об этом отказе пишем сразу).

## Verification

- Go: тесты на старт с переопределением, на старт в активность без проекта, на правку одной сессии, на отказ для выставленной сессии, на отчёты по действующему проекту, на записи аудита внутри и при откате.
- Архитектурные гварды (`scripts/check-architecture.sh`, требуется `rg` в PATH).
- e2e: правка проекта одной сессии на странице проверки, проверка записи в журнале.
- Полный прогон `make verify` в zsh перед пушем.

## Open questions

- Нет. Решения D1-D5 приняты по умолчанию; при несогласии правим design до apply.

## Решения, принятые при apply

- **Колонка без внешнего ключа.** `sessions.project_id` как у `activities.project_id`: проект удаляется вместе со ссылками, без новой политики удаления. Отличие от первой формулировки задачи 1.1.
- **Назначение проекта активности при старте** делает `StartSession` в той же транзакции через `sessionOwnProject`. Если у активности нет проекта и ни одна её сессия не в счёте, проект становится её первым проектом, как и раньше для участников. Иначе выбранный проект уходит в сессию как собственный. `resolveActivity` проект больше не назначает.
- **Ручной ввод** прошедшей сессии идёт тем же правилом: `CreateClosedSession` принимает проект и передаёт его в `sessionOwnProject`. Это расширение задачи 3.x: тот же перенос истории, и исправлять его одним решением удобнее.
- **Выставленная сессия.** Спецификация запрещает смену проекта при любом статусе счёта. `lockSessionForEdit` блокирует только счета в статусе «отправлен» и «оплачен», поэтому проверка по `invoice_id` добавлена отдельно, и черновик тоже блокирует смену проекта.
- **Наследование.** Выбранный проект, равный проекту активности, не сохраняется на сессии: сессия продолжает следовать за активностью.
- **Действующий проект в списках.** В `sessionSelect` колонка `activity_project_id` отдаёт действующий проект сессии. Поэтому список, отчёт и редактор показывают проект сессии, а не активности.
- **Аудит.** Одна строка на изменённое поле: `action = session.edit`, `target = session:<id>`, `meta = поле: было -> стало`, IP из запроса. Строки пишутся в транзакции правки.
- **Редактор.** Смена проекта в редакторе отправляет только `project_id` и сохранённую заметку (сервер перезаписывает заметку). Остальные поля не отправляются, потому что нулевая длительность отвергается. Смена подтверждается диалогом, который называет активность.
- **Миграция истории** (`invoice_legacy.go`, 2026-09-27) не меняется: она разовая, колонка в её момент пустая.
