# Design

## Context

Клиенты живут в `internal/clients` и таблице `clients`, проекты и задачи в `internal/db` и `internal/tasks`, сессии в `sessions`. Токены `pt_` выдаются через `Auth.Identity.APITokenByRaw`, у них есть флаг «только чтение». `/api/v1` уже отдаёт сессии, проекты, клиентов, теги и задачи под токеном. Архитектурная проверка (`scripts/architecture`) не даёт транспорту ходить в обход сервисов и требует роль для каждого пакета. См. proposal.md, раздел «Why».

## Goals / Non-Goals

**Goals:**
- Один набор сущностей для экрана, `/api/v1` и MCP: инструмент MCP вызывает тот же сервис, что и HTTP.
- Права в транзакции, а не в маршруте: так же, как для клиентов и выплат.
- MCP без новых зависимостей: JSON-RPC поверх HTTP на стандартной библиотеке.

**Non-Goals:**
- Настраиваемые стадии, сделки с несколькими валютами, автоматические письма, синхронизация с внешними календарями, OAuth, SSE.

## Decisions

**D1. Таблицы.** `crm_contacts(id, team_id, client_id, name, role, email, phone, created_by)`, `crm_deals(id, team_id, title, stage, client_id NULL, contact_id NULL, owner_id, amount_cents, currency, probability, close_date, next_step_at, lost_reason, created_at, updated_at)`, `crm_activities(id, team_id, client_id NULL, deal_id NULL, kind, body, result, occurred_at, author_id)`, `calendar_events(id, team_id, title, starts_at, ends_at, location, notes, project_id NULL, client_id NULL, shared, created_by)`, `calendar_event_participants(event_id, user_id)`. Все времена в том же TEXT-формате, что у остальных таблиц (`FormatTime`). Суммы в копейках, как везде (`internal/money`).
Альтернатива: положить сделки в `clients` колонками. Отклонено: сделок несколько на клиента, а стадия у каждой своя.

**D2. Стадии фиксированы в коде.** Значения `new`, `working`, `proposal`, `won`, `lost` проверяются и в сервисе, и в `CHECK`-ограничении. Переименование в интерфейсе идёт через словарь. Настраиваемые стадии потом: отдельная таблица стадий и миграция `stage` с ссылкой.

**D3. Права.** Сделка: руководитель видит и меняет все, участник только свои (`owner_id = user`). Контакт и активность наследуют права клиента. Событие календаря: автор, участники, руководитель видят; `shared = 1` видят все участники пространства. Проверка в SQL внутри транзакции, как `lockTeamRole`. Маршрут только проверяет вход.

**D4. Пакеты.** `internal/crm` и `internal/calendar` это workflow-пакеты с сервисами и портами под `db`. `internal/mcpwire`: leaf без зависимостей: типы JSON-RPC, кадрирование запроса и ответа, коды ошибок. Инструменты и HTTP-обработчик `/mcp`: в `internal/web` (транспорт, единственный, кто видит граф сервисов). Все три классифицируются в `scripts/architecture/40-package-roles.sh`.

**D5. MCP поверх HTTP без сессий.** `POST /mcp` принимает один объект или пакет JSON-RPC, отвечает JSON. Без `Mcp-Session-Id`: каждый запрос несёт токен, состояние не нужно. Версия протокола: `2025-06-18`. Версию `2026-07-28` (по обзору она добавляет заголовки `Mcp-Method` и `Mcp-Name`) поддержку отложим до проверки по первоисточнику: в этом change я опираюсь на вторичные обзоры, а не на текст спецификации.

**D6. Аудит агента.** Вызов записи пишет запись журнала того же вида, что и экран, с пометкой «агентом» в деталях. Источник передаётся через контекст (`requestctx`), а не новым параметром в каждый сервис.

**D7. Имена инструментов.** Латиница в стиле «сущность_действие»: `clients_list`, `client_create`, `client_update`, `contacts_list`, `contact_create`, `deals_list`, `deal_create`, `deal_update`, `deal_move_stage`, `activities_list`, `activity_create`, `calendar_events_list`, `calendar_event_create`, `calendar_event_update`, `calendar_event_delete`, `projects_list`, `tasks_list`, `task_create`, `task_set_status`, `time_session_start`, `time_session_stop`, `time_sessions_list`, `report_summary`. Описание каждого инструмента на английском (агенты читают его первым), текст ошибок на языке токена.

## Risks / Trade-offs

- [Большой объём] → инкременты: схема и сервисы CRM, календарь, MCP-протокол, инструменты, интерфейс. Каждый шаг с тестами и коммитом.
- [Совместимость клиентов MCP] → протокол 2025-06-18, тесты на `initialize`, `tools/list`, `tools/call`, и ручная проверка через `curl` и ответы на JSON-RPC.
- [Права в инструментах расходятся с экранами] → инструменты не содержат собственных проверок: вызывают сервис, а сервис проверяет в транзакции. Тест на каждый инструмент записи с ролью участника.
- [Календарь и часовой пояс] → события хранятся в UTC, показываются в поясе пространства; тест на переход через полночь.

## Migration Plan

1. Таблицы добавляются в `schema_compat.go` списком `CREATE TABLE IF NOT EXISTS`, существующие данные не меняются.
2. Модули `crm` и `calendar` по умолчанию выключены для существующих пространств; включаются в наборах «Фрилансер» и «Студия» при выборе набора или вручную.
3. Откат: новые таблицы остаются пустыми, `/mcp` отвечает 404 при выключенном флаге конфигурации, который добавляется в этот change.

## Open Questions

- Нужен ли флаг `PARATRACK_MCP` в конфиге процесса или `/mcp` включён всегда? По умолчанию включён, флаг снимает доступ целиком для окружений без агентов. Решаю при реализации, решение не меняет спеки.
- Версия протокола 2026-07-28: поддержать после проверки первоисточника (modelcontextprotocol.io). Не блокирует первую версию.
