# Design

## Context

Строка человека на расписании (`web/src/schedule/schedule-page.tsx`) считает загрузку на клиенте в `liveTotals`: по введённым в сетку минутам, а не по сохранённому плану. Там же вычисляется перегрузка: `over = planned > available`, слово «перегрузка» выводится при `live.over` в desktop-сетке. Процент `pct = floor(planned * 100 / available)` выводится рядом.

Серверный `weekLoadPercent` (`internal/scheduling/service.go`) отдаёт `LoadPercent` в `ScheduleRow` и в данные страницы (`LoadPct` в `handlers_schedule.go`). Проверено: `LoadPct` в React-странице не читается (в `web/src/dashboard/types.ts` он только объявлен). Подпись загрузки на экране строит клиент.

В `docs/PRODUCT.md` определено `Load% = planned / available`. Порога простоя нет.

## Decisions

### D1. Простой: загрузка строго ниже половины доступного времени

Простой, когда `available > 0` и `planned * 2 < available`. Это то же, что `pct < 50` по целой части, но без округления: граница 50% (20 часов из 40) простоем не является. Нулевой план при доступном времени попадает сюда, потому что `0 * 2 < available`.

Порог 50% : допущение по умолчанию, записанное здесь. Если руководитель хочет другой порог (например 30%), меняется одна константа и одна строка в `PRODUCT.md`.

### D2. Перегрузка важнее простоя

Порядок проверки: сначала `over`, затем простой. При `planned > available` простоя нет по определению, но правило явно записано, чтобы не зависеть от порядка условий.

### D3. Нет доступного времени, нет пометки простоя

При `available = 0` простой не выводится никогда. Перегрузка ведёт себя как сейчас: `over = planned > 0`, то есть любой план при нулевой норме перегрузка. Процент при нулевой норме остаётся 0, как и было.

### D4. Одно правило на клиенте, в отдельном модуле

Правило выносится в чистую функцию `loadState(planned, available)` в `web/src/schedule/load-state.ts`, возвращающую `"overload" | "idle" | null`. Страница использует её вместо встроенных условий. Так правило проверяется unit-тестом без браузера, как `plan-load.ts` для отчёта.

Серверный `weekLoadPercent` не меняется. Если когда-нибудь `LoadPct` начнут выводить, порог надо взять из того же модуля; это записано как риск.

### D5. Слово и место

Ключ `sch.idle`: ru «простой», en «idle» (по образцу `sch.overload`). Слово выводится в той же строке, сразу после процента. Перегрузка и простой не могут быть одновременно: при перегрузке простой не проверяется. Цвет простоя : приглушённый (`text-muted-foreground`), как и обычная строка: простой не тревожит так, как перегрузка (`text-destructive`).

## Risks

- Мобильная раскладка расписания не выводит процент человека, поэтому слово простоя там не появляется. Это совпадает с перегрузкой: она тоже только на desktop. Если нужно на мобильном, это отдельная задача.
- Два вычисления процента (клиент и сервер). Смягчение: подпись строится только на клиенте, сервер процент не выводит; порог живёт в одном модуле.
- Порог 50% может не совпасть с ожиданиями руководителя. Смягчение: одна константа в одном модуле и строка в PRODUCT.md.

## Verification

- Unit, `web/src/schedule/load-state.test.ts`: граница 50% (20 из 40 без простоя, 19 из 40 простой), нулевой план при доступном времени (простой), перегрузка важнее (45 из 40 : перегрузка, без простоя), нет доступного времени (null), пустой план без доступного времени (null).
- `npx tsc --noEmit -p .`, `npm run test:unit`.
- e2e на холодном стенде, два аккаунта через приглашение: владелец с планом 15 часов из 40 видит «простой» и процент 37; участник с планом 45 часов из 40 видит «перегрузка» и не видит «простой».
- `make ui` (бандл), `make verify` с `GOTOOLCHAIN=go1.27.3`, `scripts/check-architecture.sh`.

## Open questions

- Порог 50%. Если руководитель хочет другой, меняется одна константа. Вопрос записан, пользователь ответит при apply или позже.
- Слово в английской версии: «idle» или «underloaded». Сейчас «idle», как и в бэклоге по смыслу.
