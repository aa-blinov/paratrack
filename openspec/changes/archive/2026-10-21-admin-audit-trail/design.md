# Design

## Context

Журнал пишется двумя путями. Веб-обработчики вызывают `s.audit(r, ...)` уже после действия: ошибка записи только логируется (`web/audit_adapter.go`), поэтому строка может не появиться, а действие при этом прошло. Правка сессии пишет строки внутри своей транзакции (`internal/db/session_audit.go`): отклонённая правка не оставляет следа. Для удалений нужен второй путь.

Текущее состояние:
- `RemoveTeamMember` (`internal/db/team_members.go`) открывает транзакцию, но журнал не пишет; `handleAPIMemberRemove` журнала тоже не трогает.
- `DeleteInvoice` (`internal/db/invoice_transitions.go`) держит транзакцию и номер счёта уже прочитан (`SELECT status, number ... FOR UPDATE`), но строки не пишет.
- `RestoreWorkspace` (`internal/db/workspace_restore.go`) создаёт пространство в своей транзакции; новое пространство начинается с пустого журнала.
- `auth.Service.CreateAPIToken` пишет `auth.api_token_create` с именем токена в meta; `DeleteAPIToken` пишет `auth.api_token_delete` с пустой meta.
- `requestctx.ClientIP(ctx)` уже используется в `teamops`, `importing` и `mailqueue` для IP в журнале; `internal/db/scope.go` импортирует `requestctx` в том же пакете.

## Decisions

### D1. Удаления пишутся в той же транзакции, что и удаление

Новый помощник `auditInTx(ctx, tx, teamID, actorID, action, target, meta, now)` рядом с `Audit` в `internal/db/audit.go` вставляет строку тем же `tx`. Его вызывают три операции: удаление участника, удаление счёта, восстановление. Так же работает `sessionEditAudit`: нет действия без строки и нет строки без действия.

IP берётся из `requestctx.ClientIP(ctx)`, а время из `d.currentTime()`, как у `Audit`. Полей IP в `TeamMemberRemovalRequest` и `InvoiceMutationRequest` не добавляем.

### D2. Удаление участника: имя читаем до удаления

`RemoveTeamMember` читает имя участника в той же транзакции до удаления строки membership, потому что после удаления имя в meta некуда взять без джойна на удалённую запись. Target: имя участника, meta: `user:<userID>`. Журнал выводит цель, а meta не выводит, поэтому человеческое значение идёт в цель. Email не пишем. Имя видно администраторам и так, через состав; email в журнале не пишем.

Самоуход участника (`callerID == targetUserID`) тоже пишет `member.remove` с тем же именем в meta. Автор и цель совпадают, и по этому журнал отличает уход от удаления. Отдельная meta «сам» была бы текстом на одном языке в данных, которые видны на обоих языках интерфейса.

### D3. Удаление счёта

Строка пишется перед `tx.Commit()` в `DeleteInvoice`: target: `number`, уже прочитанный под блокировкой, meta: `invoice:<id>`. Отказ `ErrInvoiceNotDraft` выходит раньше записи и строку не оставляет.

### D4. Восстановление: первая строка нового журнала

`RestoreWorkspace` пишет `workspace.restore` внутри своей транзакции, после создания пространства и импорта. Актор: `CallerID`, то есть будущий владелец. Meta: «участников: N, счетов: M» по итогам импорта. Если строка не записалась, откатывается и восстановление: пространство без первой строки не создаём.

### D5. Отзыв токена называет токен

`DeleteAPIToken` возвращает имя токена (`DELETE ... RETURNING name`, Postgres) и `auth.Service` пишет его в meta. Выдача уже делает так же. Старые строки `auth.api_token_delete` с пустой meta не трогаем.

### D6. Подписи

Новые коды получают `audit.act.member.remove`, `audit.act.invoice.delete`, `audit.act.workspace.restore` в ru и en. `audit.act.auth.api_token_delete` уже есть. Паритет словарей проверяет `go test ./internal/i18n`.

## Risks

- Строка в транзакции делает удаление зависимым от журнала: если вставка падает, удаление откатывается. Для пяти полей и одной таблицы это приемлемо; сбой вставки означает проблему с базой, а не с журналом.
- Блокировки при удалении счёта: вставка в `audit_log` не берёт блокировок на `invoices` и `sessions`, порядок блокировок из `DeleteInvoice` не меняется.
- Имя участника в meta. Смягчение: только имя, без email; журнал виден тем же людям, что и состав.

## Verification

- Go, `internal/db`: строка `member.remove` есть после удаления и её нет при отказе для владельца; строка `invoice.delete` есть для черновика и её нет для отправленного счёта; самоуход пишет строку.
- Go, `internal/db`: `RestoreWorkspace` даёт первую строку `workspace.restore` с числами из файла; при ошибке записи восстановление откатывается.
- Go, `internal/auth`: отзыв токена пишет имя в meta.
- `go test ./internal/i18n`: паритет новых ключей.
- e2e на холодном стенде (`scripts/qa-env.sh down && up`): удаление черновика счёта появляется в журнале с подписью «Счёт удалён» на `/audit`; отзыв токена показывает имя.
- `make verify` с `GOTOOLCHAIN=go1.27.3`, `scripts/check-architecture.sh`.

## Open questions

- Самоуход пишем как `member.remove`, автор и цель совпадают. Если нужен отдельный код `member.leave`, это меняет подписи и фильтр; сейчас сделан один код, без подтверждения пользователя.
- Журнал не выводит meta на экран. Имя отозванного токена пишется в meta, как и при выдаче, поэтому на экране его не видно: цель там id. Варианты: выводить meta в таблице журнала или писать имя токена в цель для выдачи и отзыва. Пока не меняем, решение за пользователем.
- Запись в журнал при восстановлении ведёт в новое пространство: старое пространство, из которого выгружали, журнал не получает. Это соответствует тому, что выгрузка журнала в файл не входит.
