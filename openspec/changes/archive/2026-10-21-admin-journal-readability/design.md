# Design

## Context

Журнал читает `ListAudit` (`internal/db/audit.go`) и отдаёт `handleAuditPage` (`internal/web/handlers_audit.go`). Строка (`auditRow`) содержит четыре поля: `Time`, `Action`, `Target`, `IP`. Страница (`web/src/settings/audit-page.tsx`) выводит их как есть и подписывает действие через `audit.act.*`. Цель `targetLabel` знает только `team.modules`.

Текущие источники данных:
- `member.role`: цель: id участника (`teamops/service.go`), meta: роль (`owner`, `admin`, `member`).
- `auth.api_token_create`: цель: id токена, meta: имя токена. `auth.api_token_delete`: цель: id токена, meta: имя (после `admin-audit-trail`; старые строки без имени).
- `member.remove`: цель: имя участника, meta: `user:<id>`. `invoice.delete`: цель: номер счёта, meta: `invoice:<id>`. `workspace.restore`: цель: `team:<id>`, meta: «участников: N, счетов: M».
- `session.edit`: цель: `session:<id>`. Вне этого изменения.

Фильтр «Кто» собирается в `handleAuditPage` из `members`, а `requestedAuditFilters` принимает `user` только из этого списка.

## Decisions

### D1. Исполнитель и имена читаются при чтении

Новый метод `db.UserLabels(ctx, ids []int64) (map[int64]string, error)` читает `users` одним запросом по id. Подпись: имя, если оно непустое, иначе адрес. Так же, как в списке участников. Используется и для исполнителя, и для цели `member.role`. Бывший участник остаётся именованным, потому что учётная запись не удаляется при уходе из пространства.

Имена не пишутся в строки журнала: записи остаются как были, отображение считается при каждом чтении.

### D2. Цель и деталь собирает веб-слой по действию

Новый файл `internal/web/audit_view.go` с функцией `auditRowView(lang, entry, names, teams) (target, detail string)`. Правила:
- `member.role`: цель: имя из `UserLabels` по id из цели; деталь: подпись роли (`team.roleOwner`, `team.roleAdmin`, `team.roleMember` из словаря).
- `auth.api_token_create` и `auth.api_token_delete`: цель: имя из meta, если оно есть; если нет (старые отзывы), цель: id, как было. Деталь пустая.
- `member.remove`: цель: как записана (имя). Деталь пустая; служебный `user:<id>` не выводится.
- `invoice.delete`: цель: как записана (номер). Деталь пустая; `invoice:<id>` не выводится.
- `workspace.restore`: строка лежит в журнале того пространства, которое восстановлено, поэтому цель: его текущее название, если id из `team:<id>` совпадает с этим пространством; иначе пусто. Отдельного поиска по `teams` не нужно: название берётся один раз через `Directory.FindByID`. Деталь пустая.
- Остальные действия: цель и деталь как записаны, кроме `team.modules` (уже переводится в `targetLabel`).

Функция не знает о транспорте: она получает уже прочитанные строки и словари. Это соответствует правилам архитектуры: веб-адаптер собирает вид, данные приходят из слоя хранения.

### D3. Фильтр «Кто» строится из журнала

Новый метод `db.ListAuditActors(ctx, teamID) ([]int64, error)`: `SELECT DISTINCT user_id FROM audit_log WHERE team_id = ? AND user_id > 0`. В список фильтра попадают эти id и текущие участники. Имена берутся из `UserLabels`. Проверка `user` в `requestedAuditFilters` принимает любой id из этого списка, поэтому выбор бывшего участника начинает сужать список.

Список действий (`auditActionCodes`) не меняем: он по-прежнему строится из окна журнала.

### D4. Что остаётся кодом

Цели `session:<id>` у правок сессии и `team:<id>`, если пространство удалено, остаются как есть. Первое: отдельный пункт: правка сессии должна назвать сессию по её задаче. Второе: граничный случай, цель пустая.

## Risks

- Старые строки `auth.api_token_delete` без имени покажут id токена, как и сейчас. Смягчение: новые отзывы пишут имя; для старых ничего не восстанавливаем.
- Адреса бывших участников видны руководителю в фильтре и в строках. Смягчение: страница журнала доступна только управляющим (`s.manage`), адреса уже видны в списке участников; бывших участников без адреса в данных нет.
- `DISTINCT user_id` по журналу команды: при большом журнале запрос растёт. Смягчение: индекс `audit_log` по `team_id` уже есть (`ListAudit` его использует), список короткий (число участников и бывших).
- Подписи деталей смены роли: переводы ролей и «Изменена роль» уже есть в словаре, новых ключей не понадобилось.

## Verification

- Go, `internal/web`: `auditRowView` для каждого действия из `admin-audit-trail` и для `member.role`; старый отзыв токена без имени; пустое имя исполнителя.
- Go, `internal/db`: `UserLabels` (имя, адрес, отсутствующий id); `ListAuditActors` включает бывшего участника и не включает пустой user_id.
- Go, `internal/web`: фильтр `user` с id бывшего участника сужает список.
- `go test ./internal/i18n`: паритет новых ключей.
- e2e на холодном стенде (один владелец): строки называют владельца по имени, созданный токен виден по имени. Смена роли и фильтр бывшего участника требуют второго аккаунта и покрыты Go-тестом через настоящие маршруты `role` и `remove`.
- Бандл пересобирается (`make ui`), `make verify` с `GOTOOLCHAIN=go1.27.3`, `scripts/check-architecture.sh`.

## Open questions

- Старые отзывы токенов без имени показываем id. Если нужно другое, например «токен без имени», это отдельная подпись в словаре.
- Цели `session:<id>` остаются кодом. Если хотите, чтобы правки сессии называли задачу, это отдельный пункт, он не входит в ADM-02.
